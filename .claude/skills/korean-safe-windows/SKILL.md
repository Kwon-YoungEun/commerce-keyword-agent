# SKB 한글 파일·경로 처리

**이 스킬은 설치가 끝난 뒤의 실습에도 계속 적용한다.** 한글·공백 경로, 파일 인코딩, 화면 출력, 문서 글꼴을 다룬다. Node·Python 설치와 Windows 스토어 실행 별칭 판정이 필요하면 [setup-environment](../setup-environment/SKILL.md)의 관련 단계를 읽는다. 한글이 깨졌다는 이유만으로 환경 전체를 다시 설치하지 않는다.

수강생에게는 부드러운 존댓말로 무엇을 확인하고 어떻게 해결할지 짧게 알린다. 먼저 이 문서에서 현재 증상에 해당하는 부분만 적용한다. 사용자가 파일 하나를 읽어달라고 했는데 설치나 전체 검증부터 시작하지 않는다.

## 1. 실행 환경과 경로 전달

- 세션 정보와 실제 명령 실행 위치로 Windows·macOS·WSL·원격 환경을 구분한다. 도구 이름만 보고 OS를 추정하지 않는다. Windows에서는 실제 PowerShell을 우선하고, Git Bash 도구를 쓰더라도 PowerShell 문법은 `powershell.exe`나 `pwsh`에 명시적으로 전달한다.
- 모든 경로는 현재 셸에 맞게 인용한다. PowerShell에서는 파일 명령이 지원하는 경우 `-LiteralPath`를 쓴다. 한글·공백·괄호·대괄호·작은따옴표·달러 기호를 명령 문법으로 해석하지 않게 전달한다. 실행 파일 전체 경로는 PowerShell의 `&`로 호출한다.
- Python은 `.skb-setup-status.md`에 기록된 가상환경의 실제 실행 파일을 확인해 사용한다. Windows의 `.venv\Scripts\python.exe`, macOS의 `.venv/bin/python`은 기본 후보일 뿐, 다른 이름으로 준비되었을 수 있다. 경로를 확인하지 않고 맨 `pip`이나 기본 `py`로 바꾸지 않는다.
- 명령 도구의 작업 폴더 옵션이나 인자 배열을 우선한다. Python의 `subprocess.run`은 실행 파일과 인자를 리스트로 전달하고, 경로를 합쳐 `shell=True`로 실행하는 방식을 피한다. 명령마다 새 셸이 생길 수 있으므로 이전 호출의 변수·작업 폴더가 유지된다고 가정하지 않는다.

## 2. 같은 한글처럼 보이는데 파일을 못 찾을 때

맥에서 만들었거나 다른 환경에서 옮겨온 이름은 자모 분리형(NFD)일 수 있다. 코드의 이름이 완성형(NFC)이면 눈에는 같아도 비교 결과가 다를 수 있다. **이름은 비교할 때만 NFC로 바꾸고, 파일 작업에는 디렉터리에서 얻은 실제 경로를 쓴다.**

예를 들어 현재 폴더에서 `03_실적데이터`를 찾을 때의 짧은 패턴이다. 다른 이름을 찾을 때는 비교 대상만 바꾼다.

```python
from pathlib import Path
from unicodedata import normalize

parent = Path.cwd()
wanted = normalize('NFC', '03_실적데이터')
matches = [p for p in parent.iterdir()
           if p.is_dir() and normalize('NFC', p.name) == wanted]
if len(matches) != 1:
    raise ValueError('대상 폴더가 없거나 둘 이상입니다. 실제 목록을 확인하세요.')
target = matches[0]
```

- 하위 폴더도 같은 방식으로 찾는다. 전체 검색이 필요하면 `rglob('*')`로 열거한 뒤 이름을 정규화해 비교한다. `glob('*한글*')`나 `'한글' in p.name`만으로 NFC/NFD를 처리했다고 생각하지 않는다.
- 여러 파일이 같은 정규화 이름에 해당하면 첫 항목을 자동 선택하지 않는다. A/B 표시와 확인된 내용 차이로 구별해 보여준다. 화면상 같으면 원래 이름의 코드 포인트를 보조로 제시한다.
- 기존 경로 문자열 전체를 정규화해 다시 만들거나, 원본 이름을 일괄 변경하거나, 실습 폴더를 옮겨 해결하지 않는다. **새 파일**을 만들 때 한글 이름을 쓰는 것은 괜찮다. 문제는 기존 파일의 실제 이름을 확인하지 않고 재구성하는 것이다.
- `PYTHONUTF8=1`이나 `chcp 65001`은 이름의 NFC/NFD 차이를 해결하지 못한다.

## 3. 파일 내용과 화면 출력을 나눠 확인

Python은 `-X utf8`로 실행한다. 새 텍스트를 읽고 쓸 때는 `encoding='utf-8'`을 명시한다. 기존 파일은 BOM과 원본 형식을 확인한다. UTF-8 읽기가 실패하면 원본이 CP949 등인지 근거를 보고 판단한다.

**한글 화면 출력이 비거나 깨져도 파일 내용까지 손상됐다고 단정하지 않는다.** 다음 순서로 확인한다.

1. 종료 코드와 실행 파일을 확인한다. Windows의 Bash 출력에서만 문제가 생겼으면 같은 작업을 실제 PowerShell에서 짧게 확인한다.
2. 이번 작업 전용 경로에 결과를 UTF-8 파일로 저장하고 AI의 파일 읽기 도구로 연다. 기존 `_out.txt` 같은 이름을 무조건 덮어쓰지 않는다.
3. 저장된 내용이 정상이라면 파일 처리 성공과 콘솔 표시 문제를 따로 알린다. 이후 결과도 파일로 보여준다.
4. 명령 전달 과정에서 한글 코드 자체가 손상되면 파일 편집 도구로 짧은 작업·검증 코드를 저장해 실행할 수 있다. 이를 이유로 일괄 설치 스크립트를 만들지는 않는다.

내용 검증에서 `errors='ignore'`나 `errors='replace'`로 글자를 버리거나 바꿔 성공 처리하지 않는다. 자식 프로세스 출력은 해당 프로그램의 실제 인코딩으로 읽는다. 모르면 바이트로 받아 확인한다. 진단 로그를 대체 문자로 보여준 경우에는 원문 보존·한글 정상 판정의 근거로 쓰지 않는다.

기존 프로젝트 설정을 먼저 확인한다. 필요하면 `.claude/settings.local.json`의 `env`에 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`만 병합할 수 있다. 다른 키와 권한을 보존한다. 설정이 이미 들어 있다고 가정하지 않으며, 현재 명령은 `-X utf8`과 명시적 파일 인코딩으로 처리한다. 시스템 로캘 변경이나 `setx`로 PC 전체 설정을 바꾸지 않는다.

## 4. CSV·엑셀·문서의 한글

엑셀에서 바로 열 CSV는 **UTF-8 BOM(`utf-8-sig`)**으로 저장한다. Python의 `csv` 모듈을 쓸 때는 `newline=''`도 지정한다. pandas에서는 다음처럼 쓴다.

```python
df.to_csv(output_path, encoding='utf-8-sig', index=False)
```

기존 CSV는 실제 인코딩으로 읽는다. 데이터가 없는 것과 읽기에 실패한 것을 구분한다. 저장 후 CSV의 BOM과 한글 머리글·값을 다시 읽어 확인한다. XLSX는 저장 후 다시 열어 시트명과 한글 셀 값도 확인한다.

Word·PPT·PDF·차트에서 한글이 네모로 보이면 인코딩과 별개인 **글꼴 문제**일 수 있다. 파일의 글자 데이터가 정상인지 먼저 확인하고, 설치된 한글 글꼴을 선택해 다시 렌더링한다. Windows는 맑은 고딕, macOS는 Apple SD Gothic Neo·AppleGothic 등이 후보이며 실제 설치 여부를 확인한다. 웹은 외부 폰트가 차단되어도 읽히도록 시스템 글꼴을 대체로 지정한다.

차트 라이브러리는 필요할 때만 설치한다. matplotlib은 설치된 한글 글꼴과 `axes.unicode_minus=False`를 지정한다. Plotly도 이미지로 저장할 때는 글꼴을 명시하고 실제 결과를 확인한다. 이 작업의 디자인 색상은 실습 루트의 `CLAUDE.md`를 따른다.

## 5. 한글 사용자명 때문에 설치가 실패한 경우

`C:\Users\홍길동`처럼 한글 사용자명을 발견했다는 이유만으로 바꾸지 않는다. 오류를 읽어 네트워크·인증서·권한·호환 배포 파일 부재·경로 문제를 구분한다. 파일 작업이 정상이라면 추가 설정 없이 계속한다.

실제 패키지 설치가 필요하면 [setup-environment](../setup-environment/SKILL.md)의 패키지 설치 단계를 읽는다. 미리 빌드된 배포 파일을 우선하고, 임시 경로 오류가 확인된 경우에만 쓰기 가능한 영문 임시 폴더를 먼저 만든다. **같은 설치 프로세스**에 `TEMP`·`TMP`를 전달하고 `tempfile.gettempdir()`로 실제 적용을 확인한다. 없는 경로를 지정하거나 `C:\`에 누구나 쓸 수 있다고 가정하지 않는다. 바꾼 세션 변수는 작업 후 복원한다.

계정명·사용자 프로필·원본 폴더를 변경하지 않는다. 길이나 권한 때문에 별도 작업 위치가 필요하면 영향을 먼저 설명하고, 원본을 보존하는 범위에서 정확한 작업 대상만 정한다.

## 6. 한글 처리 검증 — 세팅 마지막 또는 관련 문제를 고친 뒤

설치 스킬에서 이 검증을 요청하거나, 방금 고친 문제의 재현 확인이 필요할 때 수행한다. 검증 때문에 Node·Python을 임의로 설치하지 않는다. 없는 도구의 검사는 **미완료**로 돌려주고 설치 여부는 `setup-environment`가 판단하게 한다.

현재 실습 폴더 안에 충돌하지 않는 전용 테스트 폴더를 만든다. 다음 작업에도 위 경로 선택 규칙을 적용한다.

1. `한글 폴더 (테스트) [1]`처럼 한글·공백·괄호·대괄호가 섞인 폴더를 만든다.
2. 선택한 가상환경 Python으로 `읽기 확인.txt`에 `SKB 한글 경로 확인: 매출 123원`을 UTF-8로 저장한다. 디렉터리 열거로 파일을 다시 찾아 읽고 전체 문자열이 일치하는지 확인한다.
3. 확인된 Node의 `fs`로 같은 파일을 읽는다. Node가 만든 별도 한글 파일도 Python에서 읽고 전체 문자열을 비교한다.
4. 한글 CSV를 `utf-8-sig`로 저장한 뒤 BOM 바이트와 데이터를 확인한다. `openpyxl`이 준비되어 있으면 작은 XLSX를 저장하고 다시 열어 한글 시트명·셀 값도 검사한다.
5. 콘솔 표시만 손상됐는지 파일 자체가 손상됐는지 구분한다. 확인이 끝난 테스트 자료는 이번에 만든 정확한 경로만 정리한다.

각 검사 결과를 **성공 / 실패 / 도구가 없어 미완료**로 알려준다. 세팅 중이면 설치 스킬에 결과를 돌려주고, `.skb-setup-status.md`의 한글 검사 항목에 반영하게 한다. 일반 파일 작업 중이면 해당 작업 결과만 보고한다. 기존 환경 기록의 다른 항목은 바꾸지 않는다.
